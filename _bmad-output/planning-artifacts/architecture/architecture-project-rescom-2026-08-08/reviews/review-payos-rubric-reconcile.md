# Review: PayOS spine update (AD-25, AD-26 + map rows) — reconcile / rubric / version reality
Date 2026-10-15. Reviewer: critic. Spine read-only. Verdict: **REVISE** (6 High, 10 Medium/Low; no Critical).

Inherited ADs (AD-1, 10, 16, 17, 23, 24): AD-25/26 do not contradict them except the AD-1 reversal-link ambiguity (H5).
Solid: single-entity decision, persist-before-call, one CreditTopUp key, signature-only auth, late-full-payment-wins, edge-key reuse via proxy.ts (verified: proxy.ts adds x-rescom-edge-key for all /api/*).

## Version reality (checked with npm view + npm pack @payos/node into /private/tmp/claude-501/payos-check, nothing installed in repo)
- `@payos/node` latest = 2.0.5 (matches Stack row). SDK default `timeout` 60s, `maxRetries` 3; env vars PAYOS_CLIENT_ID / PAYOS_API_KEY / PAYOS_CHECKSUM_KEY / PAYOS_PARTNER_CODE / PAYOS_BASE_URL.
- `PaymentLinkStatus = 'PENDING'|'CANCELLED'|'UNDERPAID'|'PAID'|'EXPIRED'|'PROCESSING'|'FAILED'` (payment-requests.d.ts). The spine's last Open Question ("confirm the full status enum from types") and addendum §12 ("only partly documented") are stale: it is verifiable today and is not recorded.
- `PaymentLink` = {id, orderCode, amount, amountPaid, amountRemaining, status, createdAt, transactions[], cancellationReason, canceledAt}; `Transaction.transactionDateTime` is a string.
- `WebhookData` = {orderCode, amount, description, accountNumber, reference, transactionDateTime, currency, paymentLinkId, code, desc, counter*...}. **No `paidAt`, no status, no cumulative amountPaid.** `webhooks.verify()` only checks the `data` signature; it does not check envelope `code/success` or `data.code`.
- `webhooks.confirm(url)` exists; payOS probes the URL at registration (addendum: must return 2XX).
- No refund resource in the SDK (payment-requests, invoices, payouts only): "no refund API" claim is consistent. "No sandbox" is unverifiable from types.

## High findings
**H1. FR-76 status model absent (AD-25 diagram + AD-26).** FR-76 lists Processing, Successful, Cancelled, Expired, Refund Requested, Refunded, Refund Rejected, and "every status change sends a notification". Spine statuses: PROCESSING, SUCCESSFUL, AMOUNT_MISMATCH, CANCELLED, EXPIRED, MANUAL_REFUNDED (+ legacy PENDING/APPROVED/REJECTED); the refund request is a separate entity while the top-up stays SUCCESSFUL. Nothing says how Wallet derives "Refund Requested/Refunded/Refund Rejected", what a user sees for AMOUNT_MISMATCH/MANUAL_REFUNDED/legacy rows, or which transitions emit notifications (only SUCCESSFUL's Outbox is stated; EXPIRED/CANCELLED by the job, mismatch outcome, FR-35 "user is notified of the outcome" are silent). Backend DTO, notification and Wallet stories will diverge.
Fix: add to AD-25: "Wallet status is a projection: SUCCESSFUL + TopUpRefundRequest {PENDING→Refund Requested, REFUNDED→Refunded, REJECTED→Refund Rejected}; AMOUNT_MISMATCH shows 'Under review'; MANUAL_REFUNDED shows 'Refunded'; legacy PENDING/APPROVED/REJECTED keep legacy labels. Every status transition (including job-driven EXPIRED and mismatch resolution) writes an Outbox notification in the same transaction as the transition."

**H2. Provider mapping left open though now verifiable; webhook contract underspecified.** `paidAt` is a stored fact but neither source nor timezone is defined: the webhook has no paidAt, only `transactionDateTime` (string, not tz-marked). The 30-minute alert (FR-35/NFR-32) keys off `paidAt`, so a wrong zone shifts it by 7 h. Other gaps: (a) no rule that credit requires envelope `code==="00"` AND `data.code==="00"` AND orderCode/paymentLinkId/amount matching the row (verify() does not check these); (b) UNDERPAID exists and `amountPaid` is cumulative while webhook `amount` is per transaction, so "paid amount" for AMOUNT_MISMATCH is ambiguous, and further payments arriving after AMOUNT_MISMATCH/SUCCESSFUL are unspecified; (c) `Any failure returns 5xx` collides with the registration probe: a signature-valid sample with an unknown orderCode must return 2xx or `webhooks.confirm` fails; unknown order/duplicate must be 2xx no-op, bad signature 4xx; (d) local status PROCESSING collides by name with payOS PROCESSING.
Fix: add an adapter mapping table to AD-25: PAID→credit path if amountPaid==amountVnd; UNDERPAID→AMOUNT_MISMATCH with amountPaidVnd=GET.amountPaid (webhook amount used only when GET is unavailable, then reconciled to GET); PENDING/PROCESSING→no change; CANCELLED/EXPIRED/FAILED→terminal local mapping. State "paidAt = transactionDateTime parsed as Asia/Ho_Chi_Minh (UTC+7), stored UTC; if absent use first-seen time". State the HTTP matrix (valid+unknown/duplicate →200; bad signature→401; processing error→5xx). Replace the last Open Question's "confirm enum" with the recorded enum; keep only the retry-behavior item. Set SDK `maxRetries: 0` on `create` (retry after timeout can create a link whose response was lost) and a bounded timeout.

**H3. FR-78 resolution semantics missing in AD-26.** PRD: Refunded allowed only for a request with a hold; Rejected requires a reason; a manual refund on a hold-less request is recorded Rejected with a note and changes no balance; unresolved after 3 business days raises an Admin alert; each resolution notifies the user. AD-26 posts `REFUND_HOLD → …` unconditionally on REFUNDED/REJECTED (would fail or underflow for ineligible, hold-less requests) and has no resolution notification, no reason requirement, no 3-business-day alert. Eligibility "no spend journal since the top-up" is also undefined: which journal types count (PRD: survey publish, reopen, voucher redemption), and whether escrow-return/reward journals count. PRD measures to the submission time; spine to "since the top-up" (same, but state it).
Fix: in AD-26: "Resolution journals post only when `holdJournalId` is set; a hold-less request resolves REJECTED with no journal, REFUNDED is rejected for it. 'Spend' = any journal whose debit side is the user's USER_AVAILABLE and whose business type is in {escrow-publish, escrow-reopen, redemption} (list owned by Economy as a constant); credits and own-hold journals do not count. Resolution writes a user Outbox notification; a scheduler job alerts Admin for requests unresolved 3 business days (channel per H-ops M3)."

**H4. PAYOS_ENABLED vs manual PENDING can deadlock (AD-25 last two sentences vs FR-79).** `PAYOS_ENABLED … turns the manual endpoints off` and `Checkout is rejected while any MANUAL PENDING row exists`. If the flag is on while a MANUAL PENDING row exists, the Admin cannot resolve it (endpoints off) and checkout stays blocked forever. FR-79 requires PayOS cannot be enabled while pending exists; the spine only puts this as an ops precondition in Open Questions. Also "any" is ambiguous (global vs same user).
Fix: "Startup/flag validation refuses PAYOS_ENABLED=true while any MANUAL PENDING row exists (global). Manual submit/approve/reject endpoints remain mounted for already-PENDING rows until none remain; manual submit is off when the flag is on." Drop the checkout-rejection sentence.

**H5. AD-26 REFUNDED link vs AD-1 reversal rule.** AD-1: a correction journal has unique `reversesJournalId` and "exactly negates that original journal's entries". AD-26: REFUNDED posts `REFUND_HOLD → SYSTEM_CLEARING` "linked to the original top-up journal". That journal does not exactly negate (original was CLEARING→AVAILABLE; the hold already moved AVAILABLE→REFUND_HOLD). A story setting `reversesJournalId` violates AD-1; omitting the link violates FR-78 "linked". Brownfield: ledger.service.ts uses `reversesJournalId` with strict checks (lines ~569-626).
Fix: "The link is a non-reversal reference column `LedgerJournal.relatedJournalId` (or `TopUpRefundRequest.topUpJournalId`+`resolveJournalId`), not `reversesJournalId`; the top-up journal is never reversed via AD-1 correction." Alternatively post a true reversal of the top-up journal after releasing the hold.

**H6. "Points always equal amountVnd / 200" contradicts mismatch credit and leaves refund-hold amount ambiguous.** Mismatch resolution credits `floor(amountPaidVnd/200)` and moves AMOUNT_MISMATCH→SUCCESSFUL, so credited Points ≠ amountVnd/200. Refund eligibility ("Available ≥ the top-up's Points") and hold amount then have two readings. Brownfield `TopUpRequest.amount` is documented "Points to credit on approval" and `amountVnd` "VND the user must transfer"; the spine does not say whether `amount` is overwritten.
Fix: "`amount` = Points requested (amountVnd/200); add `pointsCredited` set by CreditTopUp/ResolveTopUpMismatch; refund hold and eligibility use `pointsCredited`; a mismatch-credited top-up refunds the amount actually paid."

## Medium / Low (10)
M1 (Med) Brownfield ratification gap: schema has `transferReference String @unique` (non-null), `TopUpStatus {PENDING,APPROVED,REJECTED}` default PENDING, `adminId/reviewedAt/rejectionReason`. Spine does not say transferReference becomes nullable, the enum is extended (not replaced), the default changes, or that the partial unique index (Prisma cannot express it; needs raw SQL migration) and the `orderCode` sequence (`@default(autoincrement())` on a non-id column or raw SQL) are hand-written migrations. Also existing key is `topup-approval:{id}` (packages/schemas top-up.schema.ts:35, ledger.service.ts creditApprovedTopUp) while AD-25 introduces `topup-credit:{id}`; say whether creditApprovedTopUp is renamed/generalized or MANUAL-only, and that MANUAL rows keep `topup-approval:`.
M2 (Med) `REFUND_HOLD` class: AD-1 requires account classes to declare unit/normal balance/overdraft policy; AD-26 omits it (must be non-negative, user-owned). Lazy `getOrCreateAccount` inside a transaction conflicts with "ascending-id lock order"; state the account is created before locks (or at user provisioning/first top-up).
M3 (Med) Operational envelope: "alerts the Admin" (30-min, 3-day, mismatch) names no channel (Outbox email, Admin Panel flag, Sentry?). No alert on reconciliation job failure/payOS outage. Reconciliation interval 1 min needs a ScheduledJob registration with lease TTL (scheduler.constants.ts has precedents at 15 s/5 min); state interval/lease and the 24 h window anchor (no `cancelledAt` column is listed; add `cancelledAt`/`closedAt`).
M4 (Med) Secrets/registration/env: env names (PAYOS_CLIENT_ID/API_KEY/CHECKSUM_KEY), TOPUP_REFUND_MAILBOX, PAYOS_ENABLED not enumerated in the AD or env.schema ownership; webhook registration (`webhooks.confirm`) is a deploy step with no owner, no per-environment rule. No sandbox plus one webhook URL per payOS channel means staging/dev must run PAYOS_ENABLED=false (or a separate payOS channel); not stated.
M5 (Med) Webhook edge: payOS traffic arrives via Vercel rewrite; `x-real-ip` will be payOS' egress, so the global AppThrottlerGuard (apps/backend/src/common/security/app-throttler.guard.ts) and any Cloudflare WAF/bot rules can throttle/block it. Rule should require a throttler skip for the webhook route and a Cloudflare rule allowing the path; "no cookie or CSRF guard" should name the opt-out mechanism. Availability now depends on Vercel for crediting (acceptable, but record it; reconciliation covers it).
M6 (Med) Transition guard: idempotency keys `topup-credit:` and `topup-mismatch:` are different, so keys alone do not stop credit after a mismatch resolution (or a late UNDERPAID→PAID). Require every transition to be a compare-and-set on `status` inside the same transaction and fix a lock order (TopUpRequest row → ledger accounts by ascending id), as AD-24 does.
M7 (Low-Med) "user cancel" in the diagram has no mechanism: cancelUrl hit (unauthenticated param), an authenticated cancel endpoint calling payOS cancel, or provider-observed CANCELLED via reconcile? Specify; safe either way because late full payment wins.
M8 (Low) FR-34 constraints (10,000–5,000,000, multiple of 200, 5-min expiry, one Processing per user) not echoed; `expiresAt = createdAt + 5 min` is the assumption the expiry job relies on. Add a one-line pointer; payOS description length limit should be checked in the adapter.
M9 (Low) Reconciliation covers "rows expired or cancelled within 24 hours"; NFR-32 says expired. Superset is fine; AMOUNT_MISMATCH rows are not re-checked, so later extra payments go unseen (see H2b).
M10 (Low) Stack row and Deferred bullet are accurate; Ownership-map Economy row is consistent. Workflow-map rows lack the Outbox/notification keys for refund submit (events named only in AD-26 text).
